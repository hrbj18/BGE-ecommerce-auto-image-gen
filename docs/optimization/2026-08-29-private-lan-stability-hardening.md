# 私网内测稳定性与速度加固：单次开发指导文档

文档日期：2026-08-29
文档状态：开发前约束，后续实现与验收必须以本文为准
适用范围：本地 Web 工作台、局域网任务提交、5 主图 + 8 详情图生成流程

## 1. 本次开发结论

本次开发目标不是继续修改提示词、模型或图片风格，而是把当前已经具备良好生图能力的项目，加固成可以在可信私网中进行多人受控测试的稳定版本。

系统继续采用“一台主机、同一时间只运行一个商品任务、单个商品内部并发生成图片”的模型。保留现有主图优先、首发并发 5、限流阶梯 `5>3>2>1`、缺图恢复并发 2、视觉返工并发 2、完成图片即时落盘和定向返工逻辑。本轮不通过同时运行多个商品任务来追求吞吐量，因为这会放大供应商限流、状态竞争和费用风险。

本轮必须解决的核心问题是：

1. 多浏览器同时提交可能穿透 `activeJobId` 检查，导致任务状态竞争和重复模型调用。
2. 上传接口没有后端资源上限，超大或异常图片可能耗尽 Node.js 内存或磁盘。
3. 运行中的工作流不能由用户取消，卡住后会长时间占用唯一运行槽。
4. `tasks.json` 直接覆盖写入，异常退出可能损坏任务历史。
5. 任务启动前没有磁盘空间保护，长期内测可能在磁盘满后连状态文件也无法写入。
6. 私网写操作没有最小访问控制，任何能访问端口的设备都能发起付费任务或删除结果。
7. 当前健康检查只说明 HTTP 服务存活，不能说明系统是否忙、磁盘是否可用、任务进程是否可控。

## 2. 当前基线与不可破坏的能力

开始开发前必须确认并记录当前 Git 提交、工作区状态和免费测试结果。任何既有用户素材和成品都不允许作为测试写入目标。

以下能力是本次回归保护对象，不能因为稳定性改造而退化：

- 固定输出 5 张 1:1 主图和 8 张 9:16 详情图，并保留拼接图、长图、提示词、报告和压缩包。
- 主图任务优先于详情页任务提交，首张图片落盘后立即出现在 Web 任务板。
- 图片生成首发并发默认为 5；限流后按 `5>3>2>1` 降级。
- 缺图恢复和可行动视觉返工分别保持最多 2 路并行。
- 已成功图片必须保留；只重试失败、缺失、尺寸错误或审核明确要求返工的图片。
- 供应商仍为 aiEcho 原生生图，图片模型、接口字段、轮询流程及 `image_urls: ["url1\nurl2"]` 合同不得改变。
- 识图与提示词扩写模型配置、Amazon/国内平台规则、English/中文语言规则和逐图提示词逻辑不属于本轮修改范围。
- 真实 API 密钥不得写入代码、测试、日志、文档或提交记录。
- 自动化测试默认只能使用 mock/stub，不得为了验证稳定性自动发起付费生图。

## 3. 本次范围

### 3.1 必须交付

- 原子任务准入和幂等提交。
- 后端上传总量、单文件、文件数量、真实图片格式和像素规模限制。
- 可取消的工作流子进程管理、硬超时和统一收尾。
- 串行且可恢复的任务状态原子持久化。
- 磁盘空间预检和明确的低空间拒绝。
- 私网写接口的最小共享令牌保护，以及收紧 CORS。
- 健康状态、忙碌状态、任务阶段、取消状态和错误原因的可观测性。
- 前端取消操作、提交冲突和资源限制的中文反馈。
- 覆盖上述行为的自动测试、无付费集成测试和局域网人工冒烟。

### 3.2 明确不做

- 不优化或重写提示词，不更换识图、扩写或生图模型。
- 不上调图片生成并发，不修改 `5>3>2>1` 基线。
- 不实现多个商品同时生图。
- 不在本轮实现完整 FIFO 多任务队列。忙时应稳定返回当前任务信息和重试建议。
- 不引入数据库、Redis、消息队列、容器集群或分布式锁。
- 不实现公网发布、账号系统、角色权限或企业级单点登录。
- 不更换 Cloudflare Tunnel、bore、Litterbox 或 aiEcho 接口。
- 不删除、迁移或重生成历史 `待作图/`、`已完成/` 数据。
- 不把自动重启当作掩盖进程生命周期缺陷的手段。先保证任务可正确取消、收尾和恢复，再另立部署任务评估 Windows 服务守护。

## 4. 总体设计

### 4.1 顶层单任务，图片层稳定并发

项目应区分两种并发：

- 商品任务并发：固定为 1。本轮通过准入租约保证任何时刻最多只有一个商品处于接收、扩写、排队、提交或运行状态。
- 图片任务并发：保留现有 5 路首发及限流降级，继续用于缩短首图和整套交付时间。

这两个并发层不能继续共用一个延迟设置的字符串变量表达。商品任务准入应成为独立、可测试的状态机。

### 4.2 先创建任务收据，再做昂贵工作

后端收到生成请求后应按以下顺序处理：

1. 校验访问令牌、请求头和总请求大小。
2. 读取或生成幂等键。
3. 原子申请任务准入租约。
4. 立即创建 `submitting` 状态的任务收据并持久化，任务 ID 从这一刻起稳定不变。
5. 解析表单并校验图片。
6. 检查磁盘空间。
7. 执行识图/需求扩写和任务素材落盘。
8. 将同一个任务更新为 `queued`，把准入租约绑定到工作流子进程。
9. 工作流完成、失败、取消或超时后，只允许持有同一租约的收尾逻辑释放运行槽。

旧任务的异步回调不得清空新任务的占用状态。

### 4.3 失败必须可解释、可恢复、无重复费用

- 请求在进入识图或扩写前失败，不得调用模型。
- 使用同一个幂等键重复提交时，应返回同一任务，不得再次调用模型或创建第二份素材目录。
- 上传或预检失败后必须释放准入槽，并把任务记录为明确的失败阶段。
- 取消和硬超时必须保留已经生成并通过校验的图片，不删除成品目录。
- 子进程的 `error`、`close`、取消和超时回调可能竞争，最终状态写入必须只执行一次。
- 服务重启时，历史任务可读取；异常中断任务必须变为可解释的 `interrupted`/`failed` 状态，不允许长期显示“运行中”。

## 5. 具体开发任务

### 任务 0：建立开发基线和隔离测试环境

目标：保证后续测试不污染真实任务，也不触发付费 API。

改动和准备：

- 记录当前分支、提交和 `git status`；开发时使用 `codex/private-lan-stability-hardening` 分支。
- 先运行现有定向测试和 `pnpm run verify:quick`，保存基线结果。
- 为 Web 后端增加可注入的目录、时钟、磁盘查询、模型扩写器和工作流启动器；生产默认值仍指向当前项目目录与真实实现。
- 测试必须使用临时目录和假的长运行子进程，不使用真实 `待作图/`、`已完成/`、`.env` 或供应商。
- 避免重写整个 `scripts/local-web-server.mjs`；优先把可独立测试的准入、上传、持久化和进程管理逻辑拆成小模块，再由服务器编排。

建议新增或抽取：

- `scripts/local-web-admission.mjs`
- `scripts/local-web-upload-policy.mjs`
- `scripts/local-web-task-store.mjs`
- `scripts/local-web-process-manager.mjs`
- 对应的 `.d.mts` 声明或改用项目当前 TypeScript 可直接检查的形式。

完成条件：测试可以启动隔离后端并精确统计“扩写调用次数”和“工作流启动次数”。

### 任务 1：原子准入、任务收据和幂等提交

目标：同时到达的请求中只能有一个新商品任务进入流程，重复请求不会重复收费。

实现要求：

- 用带唯一租约 token 的 `SubmissionGate`/等价状态机替代直接依赖 `activeJobId` 的检查与清空。
- 状态至少覆盖 `idle`、`receiving`、`submitting`、`queued`、`running`、`canceling`。
- 在表单解析和模型扩写前获取租约并创建任务收据。
- 前端每次用户主动点击生成时创建 UUID 幂等键，通过 `X-Idempotency-Key` 发送；网络重试沿用原键，用户重新发起新任务才生成新键。
- 服务端保存幂等键与任务 ID 的映射；同键请求返回已有任务，异键请求在系统忙时返回 `409`、`activeJobId`、当前阶段和建议重试时间。
- 租约释放必须比较 token；过期回调或旧子进程不得释放当前任务。
- 任意异常路径都必须进入统一 `finalizeJobOnce`/等价收尾逻辑。

完成条件：并发提交不会重复扩写、重复启动工作流，也不会把真实运行任务错误显示为空闲。

### 任务 2：上传资源保护和图片真实性校验

目标：任何单个请求都不能无限占用内存、CPU 或磁盘。

建议默认值应可通过环境变量调整，第一版采用：

- 参考图最多 5 张。
- 单张文件最大 20 MiB。
- 整个 multipart 请求最大 64 MiB。
- 需求模板最大 1 MiB，文本输入最大 20,000 字符。
- 单图最大 50,000,000 像素，单边最大 16,384 像素。
- 允许格式沿用当前 JPG/JPEG、PNG、WebP、GIF 合同，但必须通过图片解码元数据验证，不能只看扩展名或浏览器 MIME。

实现要求：

- 先检查 `Content-Length`；即使请求使用 chunked 传输，也必须在流读取过程中计数并在越界时中断，不能等 `formData()` 全部进入内存后才检查。
- 表单解析后再次检查文件数量、每个 `File.size`、模板大小和文本长度。
- 使用 Sharp 元数据或现有图片工具验证真实格式、宽高和总像素；只读取元数据，不做完整重编码，避免增加提交延迟。
- 超限分别返回 `413 Payload Too Large`；不支持或损坏图片返回 `415`/`422`；中文错误必须说明限制值和具体文件。
- 失败时清理 `.staging-*`，但不得删除任何既有正式素材或成品。
- 上传限制同时覆盖 `/api/jobs` 和 `/api/brief-expansions`。

完成条件：超大、超多、伪装扩展名、损坏文件和像素炸弹都在模型调用前被拒绝，服务内存保持受控。

### 任务 3：工作流子进程管理、取消和硬超时

目标：一个卡住的任务不能无限占用系统；用户可以安全终止并保留已完成资产。

实现要求：

- 保存当前工作流的 `jobId`、租约 token、子进程句柄、启动时间、取消标记和最终化标记。
- 新增 `POST /api/jobs/:id/cancel`。只有当前活动任务可取消；重复取消应幂等。
- 取消过程先把任务置为 `canceling`，再终止整个进程树。Windows 使用项目已有 `taskkill /pid <pid> /t /f` 路径，其他平台先 `SIGTERM`，超时后再强制结束。
- 增加可配置硬超时。默认应略大于当前生成器完整批次超时，避免服务器先于合法工作流退出；建议初始值为 135 分钟，并在真实内测数据后调整。
- 取消、硬超时、spawn error 和 close 必须汇合到同一个只执行一次的收尾函数。
- 收尾时调用现有成品描述逻辑，保留已完成图片；状态使用 `cancelled`、`partial`、`failed` 或 `done`，不能把用户取消伪装成系统失败。
- 服务器收到 SIGINT/SIGTERM 时停止接收新任务，安全结束活动工作流、持久化状态、再关闭 HTTP 服务。

完成条件：长任务可以在可控时间内终止，进程树和运行槽都被释放，已完成图片不丢失。

### 任务 4：任务状态原子持久化与启动恢复

目标：断电、异常退出或并发保存不能破坏任务历史。

实现要求：

- 所有任务状态写入经过单一串行保存队列，防止旧快照晚于新快照覆盖。
- 在同一目录写临时文件，完成 flush/sync 后再原子替换 `tasks.json`。
- 替换前保留最近一份可解析的 `tasks.json.bak`；不得把损坏主文件覆盖到备份。
- 启动时依次尝试主文件和备份；主文件损坏但备份有效时自动恢复，并写清日志和恢复事件。
- 清理遗留临时文件，但不清理用户素材和成品。
- 重启后把没有可恢复进程的 `receiving/submitting/queued/running/canceling` 任务转换为 `interrupted` 或明确失败状态，并释放服务准入槽。
- 运行锁恢复不能只依赖 PID 是否存在；至少结合锁心跳、启动时间和合理超时，降低 Windows PID 复用造成的误判。

完成条件：模拟写入中断或主 JSON 损坏后，服务仍能启动并恢复最近一份有效历史。

### 任务 5：磁盘空间预检

目标：在磁盘不足前拒绝新任务，而不是生成到一半后全面失败。

实现要求：

- 使用 Node.js 当前版本支持的文件系统空间查询能力读取输入盘和输出盘剩余空间。
- 默认最小可用空间建议为 5 GiB，并允许通过环境变量调整；同时记录总空间、可用空间和检测路径。
- 在任务素材正式落盘前和工作流启动前各检查一次。
- 低于硬阈值时返回 `507 Insufficient Storage`，不进入模型调用或工作流；接近阈值时允许管理员看到明确警告。
- `/health` 返回脱敏的磁盘状态、当前任务阶段和服务是否可接收新任务，不暴露绝对用户路径或密钥。
- 历史任务删除继续走现有成对清理逻辑；本轮不自动删除任何历史资产。

完成条件：磁盘不足模拟下不启动模型和工作流，已有状态文件仍可正常读取。

### 任务 6：私网最小访问控制和 CORS 收紧

目标：防止同一局域网中的无关设备启动付费任务或删除结果。

实现要求：

- 增加 `LOCAL_WEB_ACCESS_TOKEN`，只从本机 `.env` 读取，不进入前端构建产物、日志或任务记录。
- 写操作至少包括创建任务、扩写、取消和删除；这些接口必须验证 `Authorization: Bearer` 或统一内部请求头。
- 前端首次访问时由测试人员输入共享令牌，只保存在当前浏览器会话中；不得提交到仓库。
- 健康检查可保持无密钥访问，但不得暴露敏感任务内容。
- `Access-Control-Allow-Origin` 不再固定为 `*`。正常前端仍通过同源代理访问；需要直连后端的来源必须显式配置。
- 未配置令牌时只允许回环地址执行写操作；需要局域网写操作时必须配置令牌。这样既兼容本机首次启动，也避免误把无保护接口开放到全网卡。

完成条件：无令牌或错误令牌不能产生模型调用、文件写入或删除；正确令牌不影响现有操作速度。

### 任务 7：前端状态和操作闭环

目标：用户能看懂系统为什么不能提交、能取消活动任务，并能区分取消、失败和部分完成。

实现要求：

- 生成按钮提交期间继续保持禁用，但后端幂等性是最终保护，不能依赖单个浏览器状态。
- 系统忙时显示当前任务名称、阶段、已完成数量、首图时间和建议稍后重试，不显示泛化的“服务错误”。
- 活动任务增加取消按钮和二次确认；取消后继续展示已落盘缩略图。
- 增加 `canceling`、`cancelled`、`interrupted`、资源超限、磁盘不足、未授权等中文状态。
- 保持左侧创建任务、右侧当前反馈与统一历史任务的现有布局，不进行视觉重设计。
- 桌面和窄屏都必须检查按钮可见、错误文字不溢出、状态不会遮挡成品预览。

完成条件：两台内网浏览器看到一致的当前任务状态；取消、冲突和资源错误都有明确可操作反馈。

### 任务 8：文档、配置和交接更新

目标：其他人克隆项目后能理解新增保护，不依赖当前对话。

需要更新：

- `.env.example`：只增加空值或安全默认值，不包含真实令牌。
- `docs/handoff/CURRENT_STATUS.md`：只写已实际完成和验证的结果。
- `docs/handoff/WEB_APP.md`：记录准入、取消、上传限制、私网令牌和健康检查合同。
- `docs/handoff/DECISIONS.md`：如果“顶层单任务、不上完整队列”等成为长期决策，再更新对应决策；不要把实施流水账写进去。
- 必要的启动说明和错误排查说明。

完成条件：`pnpm run handoff:audit` 和 `pnpm run release:audit` 均通过。

## 6. 推荐开发顺序

必须按以下顺序推进，上一阶段的定向测试通过后再进入下一阶段：

1. 建立隔离测试夹具和可注入依赖。
2. 先写准入租约和幂等性单元测试，再实现任务 1。
3. 先写超限、chunked、坏图和像素炸弹测试，再实现任务 2。
4. 先写假子进程取消/超时/重复 close 测试，再实现任务 3。
5. 先写并发保存、损坏主文件和备份恢复测试，再实现任务 4。
6. 实现磁盘预检，并通过依赖注入模拟低空间，不真实填满磁盘。
7. 增加令牌保护和 CORS 测试，再接入前端会话令牌。
8. 完成前端状态、取消交互和窄屏检查。
9. 运行全部免费测试、类型检查、前端构建、handoff 和发布审计。
10. 启动本地隔离服务做故障演练，再使用两台内网设备做非付费冒烟。
11. 只有用户另行明确授权付费验证时，才用一个新 SKU 运行完整 5+8 实图流程。

如果实施中发现必须改变 aiEcho 合同、模型、提示词或图片并发基线，应暂停该部分并单独记录原因，不能把范围变化悄悄混入本次任务。

### 7.2 隔离 API 集成测试

5. 模拟工作流超过硬超时：子进程被结束，任务进入明确状态，下一任务可以提交。

7. 模拟磁盘不足：返回 `507`，不启动工作流。

## 8. 性能保护指标

本轮稳定性功能不能以明显牺牲速度为代价：

- 参考图总量不超过 25 MiB 的正常提交，资源校验在当前主机上的 P95 目标不超过 1.5 秒，不含模型扩写时间。
- mock 工作流下，新增准入、持久化和鉴权的提交开销 P95 目标不超过 300 毫秒，不含上传和模型时间。
- 主图优先顺序与图片并发基线必须保持不变。
- 已生成图片继续即时落盘和预览，不得等到 13 张全部完成后才显示。
- 取消请求发出后，测试子进程树应在 5 秒内结束并释放运行槽。
- 任务状态保存失败不得阻塞图片 stdout/stderr 处理；应串行异步保存并记录错误。

如果真实 SKU 首图耗时相对当前同条件基线恶化超过 10%，必须定位是上传校验、扩写、参考图发布、供应商排队还是本地调度造成，不能笼统归因于模型波动。

## 9. 验收标准

以下条件必须全部满足，才能认定本次开发目标达成：

### 9.1 功能验收

- 任意数量的同时提交最多启动一个新商品工作流。
- 同一幂等请求不会重复扩写、重复写素材或重复生图。
- 上传数量、单文件、总请求、文本长度、真实格式和像素规模均有后端硬限制。
- 活动任务可取消，取消和超时不会删除已完成图片。
- 任务结束的所有竞争回调只能最终化一次，旧回调不能释放新任务。
- 任务状态采用串行原子保存；主文件损坏后能从有效备份恢复。
- 低磁盘时在模型调用前拒绝任务，并返回明确中文原因。
- 私网写接口在局域网模式下必须有令牌；CORS 不再无条件为 `*`。
- 健康检查能区分可接收任务、忙碌和资源降级状态。
- 前端能显示忙碌、取消中、已取消、中断、上传超限、磁盘不足和未授权状态。

### 9.2 稳定性验收

- 20 路并发提交测试中，工作流启动计数严格为 1。
- 超限和坏图测试不会使后端进程退出，且模型调用计数为 0。
- 取消测试在 5 秒内结束假子进程树并允许提交下一任务。
- 状态写入故障和损坏恢复测试不丢失最近一份有效任务历史。
- 服务重启后不存在永久 `running` 状态或无法解释的占用槽。
- 所有测试完成后不存在残留测试服务、工作流进程、临时素材目录或锁文件。

### 9.3 回归与速度验收

- `pnpm run verify:quick` 通过。
- `pnpm run verify:free` 全部通过，0 个失败、0 个未经解释的跳过。
- `pnpm run handoff:audit` 和 `pnpm run release:audit` 通过。
- 前端生产构建和类型检查通过。
- 图片层主图优先、5 路首发、`5>3>2>1`、恢复 2 路、返工 2 路均未改变。
- mock 性能指标达到第 8 节要求；未授权真实 API 时，报告中必须明确写“真实供应商速度尚未验证”，不得伪称完成真实速度验收。

### 9.4 数据与安全验收

- 未修改、删除或覆盖任何既有 `待作图/` 和 `已完成/` 内容。
- 没有真实 API key、私网访问令牌、Cookie、日志、客户图片或历史成品进入 Git。
- 测试只使用临时目录和假供应商。
- Git 变更只包含本次目标所需代码、测试、配置样例和 handoff 更新，没有顺手重构大文件。

## 10. 停止条件与范围变更

出现以下情况时应停止相应实施并记录，而不是自行扩大范围：

- 必须更改 aiEcho 请求合同或 `image_urls` 格式才能继续。
- 必须更换识图、扩写或生图模型。
- 必须让多个商品同时生图才能满足需求。
- 必须引入数据库或外部队列服务。
- 需要真实付费调用才能继续，但用户尚未明确授权。
- 发现现有用户改动与本次目标文件冲突，无法安全保留。

允许在不改变目标和验收标准的前提下调整内部文件名或模块边界，但必须在最终交付中说明原因，并同步更新本文中已经失效的实现路径。
