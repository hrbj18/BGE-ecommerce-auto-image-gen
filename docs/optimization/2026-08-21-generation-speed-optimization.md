# 单次优化任务指导文档：首图优先、稳定并发与后台质检

状态：已完成（未执行付费实图；已完成模拟回归与构建验证）  
日期：2026-08-21  
适用范围：本次性能与交互闭环优化；不改变商品事实、提示词质量规则、图片供应商协议或 5+8 成品合同。

## 1. 现状与问题判断

最近的真实 5+8 任务证明质量闭环可用，但从提交到可交付耗时过长。复盘表明，主要问题在编排而不在提示词：

- 运行配置将 OpenAI 首发并发设为 13，超过上游实际并发承受能力，触发 429 后才退回到 5。
- 429 默认退避为 60 秒；多个首发失败会把可用吞吐转换为长时间空等。
- 首批失败后的缺图恢复固定串行；视觉审核确认失败后的返工也固定串行。
- 前端仅显示“生成中”，没有首图优先、阶段、已完成数量、重试或质检状态；即使图片已落盘，用户也无法明确知道何时可先看首图。
- 最近一次审计协议误配已经修复，但仍需将“审计”和“交付预览”彻底解耦，防止后台质检再次阻塞用户查看已经生成的图片。

## 2. 本次目标与非目标

### 必须达成

1. **首图快速可见**：队列必须保证 5 张主图先于详情页提交；主图一旦落盘，Web API 与前端立即显示已完成数量和可预览图片，不等待 13 张、视觉审核或打包。
2. **稳定并发**：默认首发并发调整为经过真实供应商验证的 5，默认并发阶梯为 `5 > 3 > 2 > 1`；禁止本机运行配置再次以 13 作为默认首发值。
3. **快速恢复**：缺图恢复与视觉返工都采用受限并发，默认 2；不得覆盖原图，候选图通过文件/尺寸校验后才替换。
4. **后台质检**：首批图片可查看后，视觉审核、定向返工、拼接和打包继续在后台；任务状态要区分“首图交付”“批量生成”“质检返工”“打包完成”。
5. **可观测性**：任务接口持久化阶段、5/8/13 已完成数量、主图/详情页分别完成数、重试数、限流次数和阶段时间；前端用这些数据展示真实进度。
6. **安全回归**：不调用真实付费生图；通过单元/集成模拟验证调度顺序、并发上限、并行返工、进度解析和 UI 构建。

### 明确不做

- 不更换图片供应商、模型、密钥、请求体、参考图传递方式或 API 路径。
- 不降低 2K 输出、5+8 数量、尺寸校验、身份一致性、提示词审核或最终视觉审核标准。
- 不把视觉审核改成严格阻断；审核异常仍应显式标为待复核，不能吞掉结果。
- 不为压缩时间而重生成所有图片；只针对可行动的审核失败项定向返工。

## 3. 设计方案

### 3.1 双优先级生成队列

所有提示词仍一次性编译，但调度队列分为：

1. `main`：5 张主图，索引顺序先提交；
2. `detail`：8 张详情页，只在主图已占用首发槽位后补入空闲槽位。

这不牺牲完整套图吞吐：稳定并发 5 时先发 5 张主图，任一主图完成即由详情页补位。用户最快可看到首张主图，而详情页持续并行生成。

### 3.2 供应商友好的调度

- 默认并发 5，环境变量上限收紧为 8；超出时进行保护性钳制并在日志中记录。
- 限流后按阶梯降并发；重试采用较短、有限、带抖动的退避，避免多个任务在同一秒重新冲击上游。
- 记录每一次限流、退避、重试和实际并发，用于后续按供应商实测调参。

### 3.3 并行定向恢复

- 缺图恢复使用可配置但默认 2 的受限队列；原始失败原因保持在审计记录中。
- 视觉审核返工也默认并发 2；每张使用临时候选文件，通过验证后原子替换。
- 最后只做一次集合复审；协议缺项不可触发返工。

### 3.4 后台阶段与预览

生成器输出机器可读的阶段事件；本地 Web 后端解析后将进度写入任务状态。前端显示：

- 当前阶段和说明；
- 主图 `x/5`、详情页 `y/8`、总计 `z/13`；
- 已出现的图片缩略预览；
- 限流/重试与质检返工提示；
- 首图到达、首批完成、最终完成的实际耗时。

任务在后台质检时仍属于运行态，但已有图片应可点击查看，不把“最终打包完成”误称为“第一张图可用”。

## 5. 验收标准

- 在模拟的 13 图任务中，前 5 次提交均为主图；第一张完成后可立即观察到 `mainCompleted=1` 和 `firstPreviewAt`，而详情仍在进行。
- 默认配置不会以 13 并发启动；收到限流后并发按 `5 > 3 > 2 > 1` 收敛并有统计记录。
- 4 张缺图恢复、2 张视觉返工时，最多并行 2 张，且每项只处理一次候选替换。
- 在视觉审核/打包期间，任务 API 仍返回已有输出和准确阶段，前端可展示预览。
- 现有 5+8、质量审核、断点恢复和供应商兼容测试保持通过；新增测试覆盖上述速度合同。
- `npm run typecheck`、`npm test`、前端构建和 `npm run handoff:audit` 全部通过。

## 6. 风险与决策

- 上游单图实际耗时不可由本项目保证；本次保证的是避免自造长队、首图先可见和不必要的串行等待。
- 过高并发并非更快。当前以 5 为稳定基线，后续只能根据真实多个 SKU 的限流/耗时数据上调。
- 如果视觉审核真实判定多张失败，最终完成仍会受返工影响，但用户可以先查看未失败图片；是否自动交付或严格阻断保持原策略。
