# 单次开发指导：运营后台收敛与积分管理产品化

## 1. 开发目标

把当前若依通用后台收敛为面向“海客电商生图”的运营后台，并把已有积分技术验证升级为可供上线初期使用、可审计、可对账的人工充值积分系统。本次必须同时解决：积分入口 404、现有数据库不会自动获得新增表和菜单、若依官网及通用脚手架菜单过多、积分后台缺少流水与结算可见性。

## 2. 当前事实与实施假设

- 运行数据库尚无 `bge_point_*` 表和积分菜单；代码和数据库版本已不同步。
- 上线初期继续采用人工充值申请，不在没有支付渠道信息时伪造在线支付。
- 后台按小规模团队设计，账号统一为六个固定等级：体验用户、标准用户、重点用户、只读管理员、运营管理员、超级管理员；不建设企业部门和子账号体系。
- 积分暂不设置有效期，不实现转赠、提现、优惠券和会员等级。
- 生图扣费继续以整数积分结算，任务提交幂等、冻结、部分退款和补图计费规则保持兼容。
- 不触发真实或付费生图；验收使用数据库、接口、故障注入和无效图片请求。

## 3. 产品与工程原则

1. 账本优先：所有积分变化必须留下不可重复的流水引用、操作人、原因和变化后余额。
2. 价格留痕：价格修改必须原子提交整张价格表并记录修改前后值，历史任务继续使用下单快照。
3. 权限最小化：查看积分、调整积分、审核充值和修改价格保持独立权限；普通门户用户不得获得后台菜单。
4. 部署一致：已有数据库与新数据库都必须在一键启动时安全、幂等地获得当前表结构和菜单。
5. 先隐藏后删代码：日常菜单大幅收缩，但暂不物理删除若依认证、审计和权限底座，降低回归和升级风险。
6. 面向异常运营：后台不仅展示余额，还必须能定位冻结未结算、账本余额不一致和过久待审核等问题。
7. 首页不硬跳无权限路由：快捷入口按当前权限显示，数据库迁移失败时不能留下可点击的 404。

## 4. 本次任务拆分

### A. 数据库部署一致性

- 将 `001`、`002`、`003` 及本次新增 SQL 纳入每次完整栈启动的幂等数据库初始化步骤。
- 新增积分管理增强表结构：价格变更历史和必要索引；保持既有账本、账户、充值和任务扣费数据兼容。
- 新增后台产品化菜单 SQL：删除若依官网和上游示例公告；隐藏系统监控、系统工具及无业务价值的部门、岗位、字典、参数、公告、菜单入口。
- 数据库初始化失败必须阻止打开业务页面，并保留诊断日志，不得带病启动。

### B. 积分服务与接口

- 增加后台积分总览：账户数、总余额、累计发放、累计消耗、冻结中任务、待审核充值、异常数。
- 增加可分页积分流水，支持用户、事件类型和时间范围过滤，并返回操作人及业务引用。
- 增加任务扣费/结算列表，支持用户、任务号和状态过滤。
- 增加对账检查：账户最新流水余额不一致、长时间冻结未结算、异常负值或非法状态。
- 后台调账必须要求原因和幂等键；重复请求只能产生一次流水。
- 充值申请分页；拒绝必须填写原因，重复审核继续保持幂等拒绝。
- 套餐价格改为整表原子保存，必须填写变更原因并写入价格历史，避免前端并发请求造成半张价格表更新。

### C. 积分管理界面

- 将单页三标签升级为：经营概览、用户账户、积分流水、任务结算、充值申请、套餐价格、异常对账。
- 所有列表具备加载、空状态、错误反馈、分页和必要过滤；待办数量在概览中可见。
- 调账、拒绝充值和改价均使用明确确认流程，展示影响对象与变更内容。
- 页面保持运营工具的紧凑布局，桌面和窄屏均不得溢出或遮挡操作。

### D. 后台信息架构收敛

- 一级菜单收敛为首页、生图业务、账号管理；积分管理归入生图业务并排在任务中心之后。
- 删除若依官网菜单和若依示例公告。
- 日常界面隐藏系统监控、系统工具、部门、岗位、字典、参数、公告和菜单管理；停用独立角色管理，把用户与管理员合并到“账号列表”。
- 账号页只展示六个中文等级和一个单选等级编辑器，不展示部门树、岗位、权限字符、菜单树、多角色组合、导入导出或分配角色。
- 新增账号默认体验用户；编辑旧多角色账号时归一为当前一个业务等级。超级管理员为内置身份，不能在页面创建、改级、停用或删除。
- 账号列表支持一个搜索框匹配登录账号、昵称和手机号，并支持按等级、状态筛选。
- 超级管理员仍可通过后续受控维护脚本恢复底层菜单，不删除底层表和控制器。
- 顶部栏移除搜索、全屏、主题、字号、若依通知等通用模板工具，仅保留导航、账号和退出。
- 首页快捷入口必须依据权限显示，名称和说明只表达海客业务。

### E. 测试与交接

- 增加数据库菜单、初始化器、积分接口、幂等调账、原子改价和异常对账合同测试。
- 执行 Java 单元/安全测试、前端严格 BGE 类型检查、两个前端生产构建、根 TypeScript 检查。
- 对同一数据库连续执行两次初始化，确认无重复菜单、重复价格、重复流水或数据损坏。
- 执行若依无付费集成测试：管理员权限、门户二次登录、欢迎积分一次性、充值审核、跨用户拒绝、Node 停机降级。
- 真实浏览器检查后台首页与积分页的桌面和窄屏布局。
- 更新 handoff 当前状态和 Web 专题，并运行 `pnpm run handoff:audit`、`pnpm run release:audit`、`git diff --check`。

## 5. 明确不在本次范围

- 微信、支付宝或其他真钱支付、退款回调和发票。
- 企业租户、部门、子账号、共享余额。
- 付费积分与赠送积分分桶、积分到期和优惠券；这些需要先确定退款和会计政策。
- 真实图片供应商调用或任何付费生图验收。
- 删除若依底层认证、权限、日志源码或修改上游许可证。

## 6. 开发流程

1. 先补测试合同，固定菜单目标、迁移入口和积分接口行为。
2. 完成 SQL 与启动器幂等初始化，先在备份后的本机数据库验证两次。
3. 完成服务层查询、对账、幂等调账和原子价格更新，再补控制器权限。
4. 完成积分管理界面和首页权限过滤。
5. 执行菜单收敛 SQL、刷新后端并进行浏览器验收。
6. 运行全部免费测试；按验收标准逐项核对，修复后重新执行受影响测试。

## 7. 验收标准

### 功能验收

- 双击一键启动后，现有数据库自动获得积分表、增强表和正确菜单；连续启动两次结果一致。
- 管理员点击“积分管理”打开真实页面，不出现 404；普通门户用户没有任何后台积分菜单。
- 若依官网、系统监控、系统工具及已明确隐藏的通用菜单不再出现在日常侧栏。
- 侧栏和动态路由不再出现角色管理；账号页完整展示三类用户和三类管理员，新增或编辑时只能选择一个等级。
- 超级管理员不能通过账号页修改、停用或删除；历史多角色账号编辑后只能保存为一个固定等级。
- 首页只向有权限用户显示可访问的快捷入口，不产生无权限或未注册路由。
- 积分总览数字与数据库一致；账户、流水、任务结算、充值、价格和异常均可查询。
- 相同幂等键重复调账只记一条流水；空原因调账被拒绝；余额不能变为负数。
- 一次价格保存要么 12 项全部成功并产生历史记录，要么全部回滚。
- 重复审核充值不会重复到账；拒绝充值必须填写原因。
- 零交付退款、部分交付按比例退款、补图只收缺口的既有规则不回归。

### 安全与稳定性验收

- 所有积分管理接口均由服务端权限保护，不能只依赖按钮隐藏。
- 列表分页有上限，查询参数受控；接口不返回密码、令牌、本机路径或完整提示词。
- 初始化、调账、审核和改价失败均有明确错误，不留下半完成状态。
- 不调用真实图片供应商，不新增或泄露密钥、密码、Cookie。

### 工程验收

- 新增专项测试全部通过；项目原有免费测试无回归。
- Java 测试、根类型检查、BGE 前端严格类型检查及两套生产构建通过。
- 数据库初始化连续执行两次通过，菜单和积分数据计数稳定。
- 桌面与窄屏截图中无文字截断、控件重叠、横向不可控溢出或关键操作不可见。
- handoff 审计、发布审计和 `git diff --check` 通过。
