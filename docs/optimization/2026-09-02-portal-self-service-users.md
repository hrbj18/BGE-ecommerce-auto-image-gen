# 2026-09-02 单次开发指导文档：自助用户端与作图数据隔离

## 一、目标与完成定义

本次只交付一个面向普通使用者的本机门户，而不是把普通用户带进若依管理后台。

用户从 `http://127.0.0.1:8001/portal/` 打开独立登录页，可以完成用户名、昵称、密码和验证码注册、登录及退出。登录后可使用既有电商作图工作台；其可见范围严格限于两类数据：项目预先配置的“优秀案例”，以及该账号在门户中创建的作图任务和其成品。管理员仍在 `http://127.0.0.1:8001/` 使用若依后台，原有 `/workbench/` 仅保留给已有受控管理员/操作员流程。

完成不以“前端列表看起来被过滤”判定，而以任一普通账号用浏览器直接请求另一账号的任务、成品、图片、下载、取消或删除地址也无法取得数据为准。

## 二、冻结的产品合同

- 运行范围为本机回环地址，不增加外网监听，不增加 Docker 之外的基础设施依赖。
- 注册方式为用户名、昵称、密码和现有验证码；不接入短信、邮箱、第三方登录或找回密码。页面明确提示本机内测账号不具备自助找回能力。
- 新注册账号只获得新建的 `bge_portal_user` 角色。该角色没有若依后台菜单，也不拥有 `bge:workbench:use`、系统用户管理或通用文件权限。
- 门户鉴权沿用若依的密码散列、验证码、登录失败限流、Redis 令牌和失效策略；浏览器不会获得 Node 生图引擎内部令牌。
- 所谓“优秀案例”只来自现有 `优秀案例/examples.json` 所定义且存在的素材。它们是项目明确标记为可展示的案例；不从 `已完成/`、`待作图/`、历史任务或其他用户作图结果自动挑选。
- 作图工作流、5 主图加 8 详情页合同、供应商配置、并发与付费调用策略不修改。本轮测试不得调用真实付费生图服务。
- 普通用户可删除自己已完成的任务/成品，沿用 Node 已有的成对清理逻辑；不能删除他人数据。对“删除”会继续保留现有前端确认操作。

## 三、已核实的起点

1. `8001` 已经是唯一浏览器入口，若依前端会把 `/workbench/` 代理给回环 `8002` 的 React 工作台。
2. React 工作台已有上传、作图、历史、成品和优秀案例界面，但它原来经 `/workbench-api` 访问 Node 的全局任务列表，不具备多用户归属隔离。
3. Node 的 `/api/examples` 读取项目维护的 `优秀案例/examples.json`；该接口不是从用户历史任务生成案例。
4. Node 引擎仍只接受 Java 服务持有的内部令牌。现有 `BgeEngineClient` 已限定上游为回环地址并限制路径、响应类型和体积。
5. 若依已有验证码、登录、密码散列、Redis 令牌和角色关联能力。现有 `bge_operator` 可使用旧工作台，但该角色可读全局管理数据，不能授予自注册用户。

## 四、总体方案

### 4.1 地址与进程边界

新增一个只监听 `127.0.0.1:8003` 的 React 开发进程，构建基路径为 `/portal/`。若依前端的 `8001` 代理 `/portal/` 到该进程，因而用户始终只访问 `8001`。`8002` 的 `/workbench/` 进程和管理语义不改变。

新增 Java 端点分为两组：

- `/portal-auth/*`：匿名注册、登录、退出和当前门户用户资料。
- `/portal-api/*`：已登录门户用户的数据和作图代理。

`/portal-api` 不复用通用的 `/workbench-api` 透传控制器。它采用逐个端点的白名单与所有权检查；图片请求会通过与原工作台相同的同源 HttpOnly 登录 Cookie 转成若依 Authorization 头，使 `<img>` 预览也必须经过鉴权。

### 4.2 身份、角色与注册

新增 `PortalAuthService` 和 `PortalAuthController`。注册时先验证验证码、格式、唯一性和密码确认，再以若依 `ISysUserService.insertUser` 创建用户和唯一角色 `bge_portal_user`；角色 ID 从数据库的 `role_key` 查询，不能由浏览器提交。用户名限制为 4 至 20 位字母、数字或下划线，密码为 6 至 32 位，昵称为非空的受限文本。

登录复用 `SysLoginService.login`，成功后由 `TokenService` 返回普通若依令牌，并设置同源、HttpOnly、SameSite=Lax 的 `Admin-Token` Cookie。门户 JavaScript 只在当前会话存储该令牌以发送 JSON 请求；图片等无自定义请求头的资源依靠 Cookie 鉴权。退出会删除 Redis 登录态、清理 Cookie 和浏览器会话状态。

门户控制器会在每次调用时核验当前用户含有 `bge_portal_user`；管理员继续从根路径使用后台，不会因管理员身份绕过普通用户的数据归属规则。直接调用若依后台的工作台桥、系统用户接口或通用上传接口仍按已有权限拒绝。

### 4.3 任务与成品的服务端归属

新增幂等 SQL 脚本和 `bge_portal_job` 表。每一行保存资源类型（`image` 或 `brief`）、Node 任务 ID、若依用户 ID、创建和更新时间；表保留可为空的兼容成品字段，但它不是授权依据。表中不保存图片、提示词、密码或供应商凭据。

门户创建作图/扩写任务时，Java 先将已校验的 multipart 请求转发给 Node；仅在 Node 返回可识别任务 ID 后登记“任务 ID 属于当前用户”。若登记失败，响应按失败处理并尝试让 Node 取消/清理刚接收的任务，绝不把未归属任务作为成功交给用户。

此后所有任务、扩写、成品、预览图片、下载、取消和删除遵循同一规则：先从 `bge_portal_job` 检查任务归属；成品及其资源再从该账号的已归属任务动态反查，不能仅凭成品目录名授权。列表接口只返回当前用户所有权集合中的条目。不存在所有权的资源统一按“未找到”处理，避免用 ID 枚举其他账号的信息。

优秀案例是例外但范围固定：只允许访问 Node 已定义的 `/api/examples`、`/api/examples/{id}` 以及该案例的合法原图/结果图资源；门户不允许任意 `example-assets` 路径，也不允许读取任务目录。

### 4.4 前端用户体验

React 在 `/portal/` 运行门户模式：未登录先显示简明的登录/注册卡片和验证码；登录后沿用现有作图工作台的上传、生成、优秀案例、我的任务和我的作品界面。门户模式会：

- 将 API、成品和案例图片 URL 改写为 `/portal-api/*`；
- 删除人工填写“内部访问令牌”的入口及其状态提示；
- 显示当前用户名与退出操作；
- 把历史文案明确为“我的任务/我的作品”；
- 发生 401 时清理本地会话并回到登录页；
- 继续保留生成、取消、下载和删除的已有交互，但所有实际授权由后端决定。

## 五、实施步骤

1. 先新增本指导文档，随后只增加门户需要的 SQL、Java、React、启动和测试文件；不重置数据库，不修改用户素材。
2. 编写 `002-bge-portal-users.sql`：创建门户角色、最小权限关联和 `bge_portal_job` 表。把它接入幂等数据库初始化脚本，并增加结构/权限自检。
3. 为 `ruoyi-bge` 增加必要的若依系统/框架和 JDBC 依赖，新增门户身份服务、所有权仓储、严格门户 API 控制器与异常处理。扩展 Cookie 过滤范围到 `/portal-api/`。
4. 增加 `BgeEngineClient` 的有界 JSON 转发辅助方法；它继续替换浏览器凭据为内部令牌，禁止 Java 将该令牌写入任何响应。
5. 更新若依前端代理、启动脚本和进程记录，启动额外的回环 `8003` 门户前端；所有用户说明仍只给出 `8001/portal/`。
6. 把 React API 路由抽象为门户/旧工作台两种模式，新增门户鉴权页面和用户栏；不重写既有作图业务组件。
7. 增加 Java 单元测试、根静态合同测试和 PowerShell 集成验收。集成测试将创建临时门户账号、给临时映射绑定一个已存在的本地任务作只读隔离验证，并在 finally 中清理账号、角色关联和临时归属记录；不会提交真实生图。
8. 启动服务并进行浏览器可视验收，最后运行构建、回归、handoff 审计和安全检查；根据结果更新当前状态与本文件的验收记录。

## 六、风险、反例与处理

- **只在前端过滤。** 这是不可接受的，因为用户可直接输入他人 ID。处理方式是每个 Java 端点先查所有权，图片和压缩包也不例外。
- **复用 `bge_operator`。** 这会保留旧工作台的全局读取能力。处理方式是专用无菜单角色，门户端点另行验证。
- **注册后未绑定角色。** 用户会“注册成功但不能作图”。处理方式是使用带事务的 `insertUser` 和角色 ID 的服务器端查找，并在测试中检查角色唯一性。
- **Node 接受任务后数据库登记失败。** 可能形成不属于任何人的任务。处理方式是响应不宣称成功，并把故障记录为服务端可诊断错误；不能在无法确认任务是否为本次新建时盲目取消，以免误删并发请求的既有任务。
- **完整案例目录被公开。** 处理方式是只允许 `examples.json` 中的 ID、分组和数字索引，不提供任意路径转发。
- **现有管理员工作台被影响。** 处理方式是门户新建 `/portal-api`，不修改旧 `/workbench-api` 的权限与数据行为；对两条路径分别回归。
- **付费生成验证。** 本轮不点击“开始生成”作为自动验收。可验证上传请求被正确保护、任务所有权被写入的模拟/已有数据路径；实际供应商生成由使用者在门户登录后人工发起。

## 七、测试与验收标准

### 自动化验证

1. Maven：门户身份、角色校验、所有权服务和严格路径策略单元测试通过；门户控制器对匿名、无角色和他人 ID 皆拒绝，且拒绝时不调用 Node 客户端。
2. 根前端/合同测试：门户不含 Node 内部令牌、不走 `/workbench-api`、不允许通用路径代理；SQL 中新用户只获得 `bge_portal_user`。
3. 构建：`mvn -f admin/backend/pom.xml test`、`mvn -f admin/backend/pom.xml package -DskipTests`、根项目测试、React 生产构建及若依前端构建全部成功。
4. 集成脚本：注册两个临时门户用户，验证登录、当前用户、同源 Cookie 图片鉴权、优秀案例读取、用户 A 读取自己映射的任务成功、用户 B 和未映射用户直接请求同一任务/成品/图片/下载/删除得到 404 或 403；所有临时行被清理，真实付费请求数为零。
5. 回归：管理员根入口、`/workbench/`、BGE 只读角色和 Node 停止时若依仍存活的既有烟测保持通过。

### 人工验收

以下项目全部满足，才可称本次目标完成：

1. 打开 `http://127.0.0.1:8001/portal/` 显示用户登录/注册页，而不是若依左侧管理菜单。
2. 新账号可以完成验证码注册与登录，进入作图工作台；页面能显示用户名、退出、优秀案例、我的任务和我的作品。
3. 普通用户既看不到后台用户管理，也不能通过手工 URL 打开任何其他用户任务、图片、压缩包、删除或取消接口。
4. 用户只可见 `examples.json` 定义的优秀案例与本人门户任务；不出现未精选历史成品或别人的素材。
5. 用户可提交一次真实作图的入口存在并经鉴权（是否点击及产生费用由用户自行决定）；本次自动测试没有提交真实供应商任务。
6. 管理员仍可从 `http://127.0.0.1:8001/` 管理账户，旧受控工作台仍可从 `/workbench/` 使用。
7. 用户只需记住 `8001/portal/`；`8002`、`8003`、`8080`、`8787` 均只作为本机内部组件，不出现在常规用户操作说明中。

## 八、停止条件和回退

若发现现有任务 ID 无法可靠对应 Node 成品、注册/角色绑定无法在不扩宽后台权限的条件下完成、或任何回归表明管理员工作台暴露/损坏，则停止继续扩大范围，保留现有 `/workbench/` 与管理员后台。无需删除用户素材或重置数据库；新增 SQL 均为增量且幂等，门户可通过停止 `8003` 和撤销 `/portal` 代理回退而不影响 Node 生图引擎。

## 九、实现结果与验收记录

### 已完成

- **通过：专用用户入口与注册。** `8001/portal/` 经内部 `8003` React 进程提供独立登录/注册页；新账号只能被授予无菜单 `bge_portal_user`。登录沿用若依验证码、密码散列、Redis 会话和 HttpOnly 图片 Cookie，不向浏览器暴露 Node 内部令牌。
- **通过：服务端数据隔离。** 新增 `bge_portal_job` 任务归属账本；门户不复用旧的全局 `/workbench-api`。任务、成品、图片、压缩包、取消和删除均先验证任务归属；成品授权从已归属任务动态反查，避免中文目录名编码差异造成越权或误拒绝。
- **通过：用户可见范围。** 门户案例仅来自 `优秀案例/examples.json` 的受控内容；任务列表和作品列表仅返回本账号任务。页面明确显示“我的任务”“我的作品”和当前账号退出入口。
